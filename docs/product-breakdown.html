01 · Purpose

What the product is for

Campus Stores is a desk tool for the person at a university media-equipment counter. Clubs file requests with the Student Activities Office. Once a request is approved, someone from the club comes to the counter, collects the physical kit, and later brings it back. The tool exists so that at any moment the desk knows which physical unit is with whom, against which approval, and when it is due. It also has to keep working when the person at the counter changes between shifts.

User

The desk clerk, a student or staff member working a shift at the counter. They change between shifts, so the system is the only memory that carries over.

Core job

Issue → track → recover. Hand out approved kit to the right person, record each unit, take returns (often partial), and leave the next shift a picture of what is still out.

The exercise

A fictional, offline prototype built to be judged, not finished. The candidate works one scripted shift and answers: would you keep this product?

02 · Building blocks

What the starter is made of

The starter uses three static files. index.html holds the layout and inline SVG icons, app.js holds the sample data and interactions, and styles.css holds the desktop and mobile layouts. State lives in localStorage under campus-stores.shift.v1. The local redesign keeps this structure and adds the supplied logo.png.

Screen

Requests

3 approved forms from the Student Activities Office. Each one lists the club, the filer, a return-by time, the approved equipment types and a note. Read-only.

Screen

Inventory

8 physical units, each with an ID, model and home bin. Status is derived: In repair, On loan (open slip) or On shelf. It can be filtered.

Screen

Loan register

One issue slip per physical unit. A slip ties request + unit + collector + due time. The list shows Outstanding or All. Each slip has one-click Record return.

Screen

Desk book

Club messages (proxy pickup, overnight mic, partial return) plus free-text handover notes that one shift leaves for the next.

Control

Shift clock

The story has 3 phases: Fri 3:45 pm pickup, Fri 7:30 pm partial return, Sat 9:00 am morning shift. You can only move forward.

Rules

Issue validation

Before a slip is saved, the unit's type must be on the request, that type must not already be out on that request, the unit must not be in repair or already out, and the collector must be a known person.

Persistence

Save & restore

commit() re-renders and writes JSON on every action. restore() checks the saved data's structure before loading it. Restart sample shift resets everything.

Feedback

Status bar

A single role="status" line at the bottom. It shows confirmations ("Issued PR-04 to Kabir Sen on slip L-402.") and validation errors.

05 · Reading the brief

What reviewers are actually asking for

“Would you keep this product?”

This is a product judgement exercise, not a coding test. The shift is scripted to set three traps: a proxy pickup, a partial return, and a handover to a stranger. Each one tests whether the tool holds the truth when the person, the time, or the item changes.

The hidden success criterion is in the brief: “leave the next shift enough information to finish the job.” The morning clerk has to close the right item with no help from Friday's clerk.

  1. One moment it handles wellEvidence must be a specific action or decision from my shift.
  2. One moment I would changeSame rule: point at the click, the field, or the record.
  3. Sketch or prototype the changeWalk through the same job using it, and say what I would keep.
  4. One real-counter observationA single thing you could watch at a real desk to tell whether the change helped.

06 · Keep

The moment it handles well

EVIDENCE At 3:45 pm I tried to put the Photo Circle's camera (CA-03) on the Film Society's request, and the desk refused: “This equipment type is outside the approved request.” When I tried to add a second speaker (SP-05) to RQ-214, it refused again: “The approved quantity of this equipment type is already on loan.” PR-06, which is in the workshop, never appeared as an option.

At 7:30 pm that same model paid off. Because every physical unit has its own slip, closing the projector and speaker left exactly one open line: AD-12. The data model shows a partial return correctly. The interface around it is what lets the clerk down.

08 · Borrowing from inFlow

How inFlow keeps the customer moving

inFlow Inventory is a mature small-business inventory platform that handles the same job at a larger scale: stock leaves against an order, sometimes in pieces, and someone else has to finish it later. Below are eight design choices from inFlow's own help centre and product pages. Each is set against what Campus Stores does today and linked to the iteration that borrows it. This comes from public documentation, not a hands-on account, so visual details are inferred from the written docs.

The product-engineer reading

Five principles underneath the features

  • Work on the object the customer thinks in. People think “the Film Society's order”, not “slip L-404”. The ledger sits underneath.
  • Show state, so nobody has to remember it. Progress bars, Started/Fulfilled, and dates stamped on every step.
  • Prevent at the point of choice. Warnings appear in the field being edited, before anything is saved.
  • Make mistakes cheap. Unpick, unfulfil, and edit the date. Reversal is a normal action.
  • Every change has an owner. Each scan is tied to a person, so “who did this?” always has an answer.
Why it transfers

Same shape of problem, at a smaller scale

A club request maps to a sales order. Issue maps to pick and ship, a partial return to a partial shipment (“Started”), the morning clerk to a second warehouse picker, and the asset label to the barcode. Scale is the main difference: a campus desk has 8 units, not 8,000. So the lesson is to borrow the principles and leave the machinery. We don't need carriers, boxes, invoices or reorder points.

inFlow · order tabs

The order is the workspace

A sales order carries its own stages as tabs (Sales → Pick → Ship, or Fulfill), and turning on shipping adds the steps that apply.

09 · Change, round two

Three more iterations, inFlow-inspired

Iterations 1–3 fix single moments in the shift. These three work on the structure underneath: what the clerk's main object is, what “available” means, and who is accountable. Each one still points at evidence from my run.

Evidence from the shift

  • Requests is read-only. Every action on RQ-214 (issue, return, handover) happened in other tabs, so I hopped between four tools: Requests → Register → Inventory → Desk book.

  • The brief's morning question, “what was outstanding from the screening”, is a question about a request. The product only answers it per unit, so the clerk has to put the answer together themselves.

10 · Recommendation

Which one to put in the submission

The brief asks for one change. I would lead with Iteration 2, because it goes straight at the stated goal (“leave the next shift enough information to finish the job”), and the 7:30 pm moment is the one where the product has no place to put the truth. Iteration 3 is its morning-side half, which makes it the natural walkthrough. From the inFlow round, Iteration 6 is the cheapest high-value add-on to 2: the timestamps and clerk names are what make the “still out” record trustworthy. Iteration 5 comes next. Iteration 4 is the long-term direction (the request as the front door), and Iteration 1 falls out of it.

Side findings from the starter code (commit aeeba26)
  • paint() set advance.textContent, which wiped the arrow icon inside the button. FIXED LOCALLY The redesign updates the button label while preserving its icon.
  • Starter issue validation checks only that the collector is a known person. It doesn't check that they're linked to the request, and nothing ties the due time to request.due. PARTLY ADDRESSED The local kit form pre-fills the authorized proxy and uses the request's due time. The single-slip form still accepts any known person and any listed due time.
  • The starter's return action sets back = true without a timestamp or returned-by. ADDRESSED LOCALLY The redesign requires the physical unit label, records who brought it back and the simulated desk time, and can undo the latest return.

Current prototype. The request contains the kit checklist, issue action, status and returned-item progress. Open slips carry the expected person and arrival time. Returns require a matching unit ID and save the returned-by name and desk time. The latest return can be undone. Clerk sign-in, a complete action history, global unit lookup and reservations remain proposed work.

11 · Design sources

Where the decisions came from

The campus workflows are design interpretations of the sources below. The starter evidence comes from the fictional shift. The mini-prototypes illustrate proposals and do not share state with the staff app.

  • Supplied Campus Stores logo. The orange tag, teal loop and dark wordmark set the platform palette. Orange marks the primary action, teal marks availability and selected navigation, and neutral surfaces carry the equipment records. View the original logo.
  • Gödel Machines. Short product descriptions and distinct visual marks informed the restrained labels and equipment icons. Reference website.
  • inFlow order fulfillment. Its picking, shipping, partial fulfillment and unpick controls informed the request workspace and reversible return proposal. The campus prototype uses one slip per physical unit. Sales orders, pick, pack and ship.
  • inFlow Stockroom. User-linked stock movements and product history informed the accountability proposal. The current campus prototype records a returned-by name and desk time, while clerk identity remains future work. Stockroom workflows and records.
  • inFlow Stockroom users. Shared-device identity and optional PINs informed Iteration 6. These are research references for the proposal. Users, devices and PIN sign-in.
